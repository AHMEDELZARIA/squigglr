\subsection{Shared Responsibilities}
\label{sec:shared-responsibilities}

The following responsibilities apply to every member, regardless of
their lead roles:

\begin{itemize}
    \item \textbf{Software development:}
    Implement and maintain product features, resolve defects, and
    contribute to integration. Every member will receive substantive
    product-code tasks. Members may work across frontend, backend,
    and other technical areas with support from the relevant leads.

    \item \textbf{Testing:}
    Develop and run appropriate tests for their changes, investigate
    failures, and address defects. The Testing Lead coordinates the
    overall approach; each developer remains responsible for testing
    their own contributions.

    \item \textbf{Research and requirements:}
    Investigate stakeholder needs, domain knowledge, and technical
    approaches. Record supporting sources and assumptions, and
    contribute to defining and reviewing requirements.

    \item \textbf{Documentation:}
    Write and update the documentation associated with assigned work,
    including relevant requirements, design decisions, setup
    instructions, and test evidence.

    \item \textbf{Peer review:}
    Review teammates' code and documentation for correctness, clarity,
    and consistency with requirements and agreed standards. Each
    substantial change will be reviewed by someone other than its
    author before acceptance.

    \item \textbf{Task tracking and communication:}
    Keep assigned GitHub issues and project-board entries current,
    communicate progress and blockers, and notify the team when an
    agreed deadline is at risk.
\end{itemize}

Each substantive task will have a named owner, an agreed deadline, and
completion criteria recorded in a GitHub issue. Tasks involving multiple
components will also identify who is responsible for coordinating their
integration. These assignments establish individual accountability
within the team's shared responsibilities.

\section{Workflow Plan}

\label{sec:workflow-plan}

GitHub connects each task to its implementation, validation, and review.
The workflow below applies to code, documentation, and repository maintenance.
Authors own their changes through review and closure; reviewers check both
the completion criteria and the evidence supplied.

\subsection{Git Branches, Commits, and Review}

The planned workflow uses short-lived issue branches, \texttt{development}
for integration, and \texttt{main} for stable versions. The
\texttt{development} branch has not yet been created; current documentation
PRs, including this contribution, target \texttt{main}. Creating the branch,
aligning the README instructions, and configuring its checks and protection
are follow-up repository work. Once it is available, use this workflow:

\begin{enumerate}
  \item Select an assigned GitHub issue with clear completion criteria.
  Update local \texttt{development} from the remote, then create a branch using
  this pattern:
  \begin{quote}
    \texttt{<type>/<issue-number>-<short-description>}
  \end{quote}
  For example, use \texttt{docs/14-workflow-process}. Move the issue to
  \emph{In progress}.
  \item Make focused commits that preserve each contributor's work. Use the
  commit format below and include the issue reference. Keep unrelated changes
  in separate issues and branches.
  \item Run checks relevant to the change and inspect the results. Push the
  branch and open a pull request (PR) against \texttt{development}. Include the
  evidence needed to review it and move the issue to \emph{In review}.
  \item Address feedback, obtain at least one teammate's approval, and
  resolve review conversations. All applicable checks must pass. Substantive
  changes after approval require renewed review before merging.
  \item Merge into \texttt{development} using \textbf{Create a merge commit}.
  Confirm the issue's completion criteria, update the board, and delete the
  merged issue branch. Close work completed at this stage manually with a
  link to its PR; work requiring stable integration remains open.
  \item The affected contributors verify their combined changes on
  \texttt{development}, including applicable integration checks and manual
  user-flow or document review. Fix integration failures through reviewed
  issue branches before promoting the result.
  \item When integration is verified, open a PR from \texttt{development}
  to \texttt{main} with the included issues and validation evidence. Obtain
  at least one approving teammate other than the author, pass all applicable
  checks, and resolve review conversations. Substantive changes require
  renewed review. Merge using \textbf{Create a merge commit}, verify the
  stable result, and close the remaining completed issues. Keep the
  \texttt{development} branch for the next integration cycle.
\end{enumerate}

Allowed commit types are \texttt{feat}, \texttt{fix}, \texttt{docs},
\texttt{style}, \texttt{refactor}, \texttt{test}, \texttt{build},
\texttt{ci}, and \texttt{chore}. Use this format:

\begin{verbatim}
<type>: <short action describing the change> (#<issue-number>)

<optional explanation of why the change was needed>
\end{verbatim}

The PR title summarizes the ticket and includes its issue number. Its
description explains what changed and why, supplies validation evidence
(checks run, document review, screenshots, or preview links as applicable),
links the relevant issues, and identifies outstanding work. Use
\texttt{Closes \#<issue-number>} only when the entire issue is satisfied; otherwise use
\texttt{Refs \#<issue-number>}. GitHub's automatic issue closure applies when
the closing PR merges into the default branch, \texttt{main}; close an issue
manually if its completion criteria are fully satisfied on \texttt{development}.
The approving teammate must be someone other than the
author. Documentation reviewers use the
\href{https://github.com/AHMEDELZARIA/squigglr/blob/main/docs/Checklists/DevPlan-Checklist.tex}
{Development Plan Checklist} and
\href{https://github.com/AHMEDELZARIA/squigglr/blob/main/docs/Checklists/Writing-Checklist.tex}
{Writing Checklist}, as applicable, and inspect the generated PDF.

Merge commits preserve individual commits and attribution. Squash merging
and history rewriting on shared branches are prohibited by team policy.
To resolve integration conflicts, coordinate with affected contributors,
merge the current target branch into the source branch, resolve conflicts,
and rerun relevant checks. This means merging \texttt{development} into an
issue branch, or \texttt{main} into \texttt{development} for a promotion PR.
Correct mistakes already merged through a reviewed revert or corrective PR.

For each submitted version, the milestone Quality Assurance (QA) coordinator
checks the generated PDF and identifies the exact submitted commit with an
annotated tag, for example \texttt{submission/dev-plan-2026-09-28}. Record the
tag and commit in the deliverable's tracking issue. Preserve existing tags;
use a new revision suffix, such as \texttt{-r2}, for a corrected submission.

\subsection{Continuous Integration and Delivery}
\label{sec:ci-plan}

Continuous Integration (CI) checks proposed changes; Continuous Delivery
(CD) prepares a reviewed candidate for an authorized release. Existing
automation and planned application checks are distinguished below.

\subsubsection*{Existing Documentation Automation}
The repository's
\href{https://github.com/AHMEDELZARIA/squigglr/blob/main/.github/workflows/latex-pages.yml}
{\texttt{latex-pages.yml}} builds affected documentation on relevant PRs
targeting \texttt{main} and pushes to \texttt{main}. Its path filters cover
documentation, references, the Makefile, and documentation automation.
On pushes to \texttt{main}, it updates committed PDFs and the dependency
manifest. It also publishes the PDFs through GitHub Pages on non-PR runs,
including manual dispatch. Compilation checks syntax; authors and reviewers
must still inspect content, links, and layout.
Contributors compile PDFs locally for review but do not commit them; the
workflow updates \texttt{pdfs/} after merging to \texttt{main}. Until then,
review the local build or the PR's GitHub Actions artifact, rather than
expecting the committed PDF to contain the proposed source changes.
Before accepting a documentation check, confirm that its log lists the
changed document as compiled and that its PDF artifact matches the reviewed
source. A successful status alone is insufficient if the run reused a
cached PDF without rebuilding the changed document.

\section{Proof of Concept Demonstration Plan}

\subsection{Main Risks to Project Success}

The following features may be difficult to implement or significantly delay
project progression:

\begin{itemize}
\item \textbf{Automatic refinement:} Refining freehand drawings into supported 
shapes or objects while preserving the child's original drawing. This feature
becomes subjective for more complex shapes. The program must determine what 
will be refined and what will remain as it is. 
\item \textbf{Adaptive difficulty and guidance:} Changing the level of assistance 
based on performance or repeated difficulty will require significant user testing
along with trial and error.
\item \textbf{Browser and device compatibility:} Drawing input and interaction must
adapt to different screens (tablet, laptop) and input devices (finger, pen).
\end{itemize}

The most difficult part to implement will be automatic refinement of drawings.
Existing software has line straightening and simple shape correction, but our
program will need more unique shapes (e.g. stars, arrows, hearts), both 2D and
isometric projections, all while preserving the child's distinct style. The most 
difficult part to test will be adaptive difficulty and guidance as it requires 
multiple rounds of user and acceptance testing to tune.

There most likely won't be any libraries that are overly difficult to configure 
since the POC will use established drawing libraries like Paper.js. Shape evaluation 
will most likely be implemented from scratch using standard JavaScript functionality. 
The solution is fairly portable since it is a website that can be opened on any device 
without installation. This is especially suitable for schools where getting downloaded
software approved is tricky. Implementation and testing will focus on tablets and computers.

\subsection{POC Demonstration and Risks Addressed}

The POC will be a small web-based demonstration containing one structured drawing
lesson set and a limited creative drawing feature. 

\begin{enumerate}
\item Open the website in a browser on a laptop.
\item Select the drawing lesson set (e.g. "Quadrilaterals").
\item Display guidance level (default starting level) and metrics for demonstration.
\item \textit{Demonstrate drawing with finger and pen}
\item \textit{Demonstrate that the website can be opened in a browser on a tablet as well}
\item Complete the first tracing task (back to laptop).
\item Display simple feedback for child.
\item \textit{Show that guidance metrics are updated and calculation behind it}
\item Continue completing tasks in the lesson set.
\item \textit{Demonstrate how guidance metrics affect lesson involvement and assistance}
\item Repeatedly underperform and make mistakes on tasks.
\item \textit{Demonstrate that repeated difficulty increases assistance.}
\item Open the creative drawing area and draw a supported simple shape.
\item Apply automatic refinement and continue editing the refined result.
\item Restore the original unmodified drawing.
\item Save the attempt and display the stored attempt information in a basic history view.
\item \textit{Indicate how history will be used for performance metrics for teachers and parents}
\end{enumerate}

Opening the website on multiple devices and drawing with a finger and a pen addresses 
\textbf{browser/device compatibility}.\textbf{Adaptive difficulty and guidance} and 
\textbf{automatic refinement} are addressed through demonstration of the features.

If the POC fails, our team will meet to discuss further steps. we may turn some goals 
into stretch goals and drop some features to focus on others. We may also limit the 
scope of some features, like defining less shapes, replacing automatic refinement with 
a simpler supported correction (or borrowing from a library), and reducing adaptive 
behaviour to performance ratings, repeat levels, and a practice mode.

\subsection{Drawing Assessment and Enhancement}

The application is expected to retain drawings as editable paths and
coordinates, with the canvas displaying those paths. Enhancement will
update this drawing data and redraw the same canvas, allowing the user
to continue working on the result. The original strokes will be
preserved separately for assessment and to support undoing an
enhancement.

Paper.js provides path smoothing and simplification that the team
expects to reuse. The team will implement the application-specific
logic for recording strokes, assessing drawings, adjusting activity
difficulty, and managing enhancement actions. Initial assessment will
consider explicit measures such as deviation from a target path and
shape coverage. Initial difficulty adjustment will use rules based
on activity performance.

Basic geometric enhancement will be investigated first because it can
operate directly on the existing paths without model training.
Smoothing and simplification will be described as geometric processing,
rather than artificial intelligence.

For creative enhancement, the team will investigate an existing
pretrained multimodal model capable of accepting a drawing preview
and returning structured drawing instructions. Candidate instructions
include modifying a curve or adding a supported shape. The application
would validate these instructions before applying them to the editable
drawing. A service that returns only a bitmap image would not directly
satisfy this requirement.

No specific model has been selected, and custom model training is not
currently planned. Model selection will depend on a focused evaluation
of drawing preservation, output validity, response time, and cost.
Creative vector enhancement remains an implementation uncertainty
to investigate through the proof-of-concept work.

Our team will occasionally use LLMs like ChatGPT or Claude for this project.
For documentation, we may ask the LLM to write an initial draft given context 
text and then use that to guide our own writing, borrow ideas, or paste portions

\section{Coding Standard}

Squigglr's Next.js/TypeScript standard uses the official Next.js Core Web
Vitals and TypeScript ESLint configurations, with Prettier controlling
formatting. This follows the
\href{https://nextjs.org/docs/app/api-reference/config/eslint}
{Next.js ESLint configuration guidance} and matches the planned application
tools. Application enforcement is planned in Section~\ref{sec:ci-plan};
these tools are not yet installed.

\subsection{Application Code and Formatting}

Use TypeScript for application logic and TSX files for components containing
markup, with strict type checking enabled. Use \texttt{camelCase}
for variables and functions and \texttt{PascalCase} for components and types.
Choose descriptive names and small, focused functions. Comments explain
non-obvious decisions, assumptions, or constraints rather than restating
the code. Exceptional use of \texttt{any} or a lint suppression requires
a documented justification next to the exception and explicit review.

The planned ESLint configuration combines these rule sets:
\begin{itemize}
  \item \texttt{eslint-config-next/core-web-vitals}
  \item \texttt{eslint-config-next/typescript}
\end{itemize}
Use Prettier defaults for supported application and configuration files,
and \texttt{eslint-config-prettier}
to avoid conflicting formatting rules. Committed scripts will run ESLint,
Prettier check mode, and TypeScript strict checking locally and in CI.
Reviewers check naming, function scope, comments, and justified exceptions;
automated checks cover only the rules enabled in the committed configuration.

\subsection{SQL, Python, and Documentation}

For authored Structured Query Language (SQL) migrations, use
\texttt{snake\_case} identifiers and uppercase SQL keywords. The Backend
Lead and a teammate review schema and access-policy changes for their effect
on stored data and permitted access. The existing Python automation helpers
follow \href{https://peps.python.org/pep-0008/}{PEP 8}; reviewers check these
conventions until dedicated Python linting is introduced.

For \LaTeX{}, follow the course writing conventions and checklists, including
readable source wrapping, descriptive headings, labelled tables, and
cross-references. Authors compile changed documents and visually inspect
their PDFs for layout, links, and unresolved references before requesting
review. The current documentation workflow automates compilation only.
ESLint and Prettier do not enforce the project's Python, SQL, or \LaTeX{}
standards; those conventions require review unless dedicated checks are
introduced later.

\begin{enumerate}

    \item \textbf{Why is it important to create a development plan
    prior to starting the project?}

    \textbf{Ahmed Elzaria:}

    Creating the development plan helped me recognize that agreeing
    on a project idea does not automatically mean we agree on how
    to complete it. A team can share the same goals while having
    different expectations about responsibilities, deadlines, and
    acceptable contributions. Discussing these expectations early
    gives us a common basis for coordinating work and addressing
    problems before they affect a major deliverable.

    While developing the team roles, I initially considered
    assigning each person a narrow area of implementation.
    However, I realized that this could restrict members'
    learning and create dependence on individuals. Making every
    responsibility shared introduced the opposite problem:
    accountability became unclear. The approach I settled on
    combines named leads with shared development duties and
    explicit task ownership. This showed me that planning
    involves balancing competing needs, rather than simply
    dividing a list of tasks.

    The technology discussion also demonstrated the value of
    planning. Clarifying that enhanced drawings should remain
    editable changed what we needed from the implementation:
    returning a generated image would not satisfy that
    expectation. Identifying this distinction early helped
    expose a feasibility question before investing in an
    unsuitable approach. I therefore see the development plan
    as a starting point that makes assumptions visible and
    guides early investigation, while remaining open to revision
    as we learn.

    \textbf{Moustafa Moustafa:}

    A development plan makes it clear who is responsible for what
    before the work starts. Without one, tasks are unclear and it
    is easy for someone to say ``I don't want to do this'' with
    nothing to point back to. When we define roles, who works on
    what, how we split tasks, and which tools each person uses,
    it saves a lot of friction later.

    I have learned this from experience. On a previous project, we
    did not have a well-defined plan, and it came back to haunt us
    near the end. All three of us got busy with university just as
    some milestones were due. Nobody wanted to take them on, but
    someone had to, and the work ended up being split unevenly accross 2 people.
    With a clear plan, clearly separated tasks, and agreed
    roles, we could have avoided that situation entirely. That is
    why I think having the plan in place from the start matters so
    much for a five-person capstone team.

    \textbf{Rayan Nasrallah:}

    The benefit I found clearest was being made to sketch the
    technical implementation at a high level, because doing so
    exposed what we did not yet know how to build. Committing to a
    rough shape for the system forced questions that a feature list
    never raises on its own.
    Our discussion about keeping refined drawings editable is a good
    example: the requirement sounds straightforward until you
    consider the implementation, at which point returning a
    generated image clearly fails to satisfy it. Identifying that
    early gives us time to investigate, rather than discovering the
    problem once work depends on the wrong approach.

    These feasibility questions feed directly into scope, which
    matters more here than it would on an open-ended project. We
    have two semesters, five members, and a fixed set of deliverables
    alongside the implementation, so the amount of work a feature
    requires is as important as how valuable it is. Thinking this
    through in advance is what let us treat structured practice,
    adaptive guidance, and progress reporting as core work while
    moving camera-based tracing and letter activities to stretch
    goals. Without estimating the effort first, that judgement would
    have been guesswork.

    I also think there is a real difference between discussing these
    decisions and writing them down. Discussion can produce the
    feeling of agreement while members leave with different
    understandings of what was decided, and writing forces the
    vagueness to surface. The written plan also gives us a concrete
    reference to revise. I do expect parts of it to prove wrong once
    implementation begins, since we are planning around technology
    we have not used yet, so I see its value less in being accurate
    and more in making our assumptions explicit enough to correct.

    \textbf{Muhammad Huzaifah:}

    I see the development plan as a way to establish a shared high-level
    vision before moving into detailed implementation. Agreeing early on
    responsibilities, workflows, testing, and scheduling helps us understand
    how our individual contributions fit together and avoids conflicting
    assumptions. Recording these decisions and their reasons also gives us
    traceability: when we revise an approach, we can explain what changed
    and why. For me, the value is in making informed decisions early while
    keeping them open to revision as we learn. This gives the team a common
    starting point without treating the initial plan as fixed.

    Our discussions about commit and pull request conventions made this
    practical for me. We shared the same project goals but had different
    expectations about how contributions should be recorded and reviewed.
    Agreeing on these conventions showed me why working expectations need
    to be explicit early, so that differences do not repeatedly interrupt
    implementation later.

    \textbf{Shamil Canbolat:}

    Every team members goes into a project with different underlying 
    assumptions. If these are not expressed, discussed, compromised, and 
    agreed upon by the whole group before the project starts, problems
    in development will occur down the line. For example, meeting schedules 
    ensures that team members can frequently check in for accountability 
    and clearing up confusion while defining roles makes it clear what

    \item \textbf{In your opinion, what are the advantages and
    disadvantages of using CI/CD?}

    \textbf{Ahmed Elzaria:}

    I see the main advantage of Continuous Integration (CI) as
    giving the team consistent feedback whenever changes are
    proposed. With five members contributing, relying on each
    person to remember and reproduce every check would make
    mistakes easier to miss. Automated builds, linting, and tests
    can identify problems while the relevant change is still
    small and easier to investigate. For our documentation, an
    automated \LaTeX{} build can also reveal compilation errors
    before submission.

    Continuous Delivery or Deployment (CD) extends this process.
    Continuous delivery keeps changes ready for release, while
    continuous deployment automatically releases changes that
    pass the required checks. For Squigglr, preview deployments
    would make it easier for teammates to review an interface
    change and try it on a tablet. However, passing automated
    checks should not be treated as proof that a change is ready
    for users. Drawing responsiveness and stylus behaviour still
    need evaluation on actual devices, and a successful document
    build does not establish that its content satisfies the
    rubric.

    The main disadvantages are the effort required to configure
    and maintain the workflows, the time spent investigating
    failed runs, and the risk of trusting incomplete tests too
    much. A pipeline can pass while important behaviour remains
    untested. For example, a scoring function could produce
    consistently incorrect results if its tests use the same
    mistaken assumptions as its implementation.

    Given our timeline, I favour introducing a small set of useful
    checks first and expanding them as the application develops.
    This would allow us to gain early feedback without spending
    disproportionate effort on automation before the core
    functionality exists. Human review and device testing would
    remain part of our process.

    \textbf{Moustafa Moustafa:}

    I first saw the real value of CI/CD during my previous co-op. It was
    my first experience on a large project, and I realized that a
    codebase of that size could not function without it once more
    than a few people were contributing. The same applies on a
    smaller scale to capstone. With five people working in the same
    repository, we would constantly run into conflicts and broken
    builds without CI/CD, and it would be hard to tell which change
    caused a problem. Automated checks on every pull request catch
    issues early, make it clear which change introduced them, and
    make it much easier to roll back when something goes wrong.

    The main disadvantage is that it can become a bit of a rabbit hole. Some
    people keep improving their pipeline, adding more optimizations
    and tools, until maintaining the CI/CD takes more time than the
    actual work. There is a balance to find: the pipeline should
    be good enough to let the team work together safely and recover
    from mistakes, without being over-engineered. For us, that means
    keeping CI/CD simple and only adding to it when we actually need
    to.

    \textbf{Rayan Nasrallah:}

    Continuous Integration means merging our work into the shared
    branch frequently, with automated checks running on it each
    time, instead of integrating large amounts of work at once.
    Continuous Delivery keeps every change that passes those checks
    ready to release, while continuous deployment releases it
    without waiting for a person. Our repository already does all
    of this for documentation: a GitHub Actions workflow determines
    which documents a change affects, compiles them, commits the
    resulting PDFs, and publishes them to our project page. Once
    implementation begins, the same pipeline would run tests and
    linting rather than only document builds.

    The advantage I value most is the effect this has on how we
    work, rather than what it automates. Because every change
    arrives as a pull request that has to build before it can
    merge, work cannot sit unintegrated on a branch for weeks and
    then arrive all at once near a deadline. Changes stay small
    enough for somebody other than the author to read properly, and
    the project advances in increments we can each follow.

    The published output stays current for the same reason. Our
    PDFs always correspond to what is on the main branch, so nobody
    has to compile everything before a submission and discover a
    problem then. For the application, preview deployments would
    let the rest of the team try an interface change on a tablet
    instead of taking the author's description of it on trust.

    I initially thought there were no real disadvantages, and
    looking more carefully at our own workflow changed that view.
    The clearest cost is that a passing pipeline is easy to mistake
    for a correct result. Our problem statement compiled without
    error while citing references the document did not yet contain,
    because \LaTeX{} has no reason to object to that. The same
    failure will be available to us in code, where tests can pass
    while drawing responsiveness on a real tablet remains wrong.
    Automated checks only cover what we thought to check, so I read
    a passing run as evidence that nothing obvious broke rather
    than that the work is right.

    \textbf{Muhammad Huzaifah:}

    I view CI/CD as a technical investment. Setting up reliable builds,
    tests, and deployment workflows takes valuable time upfront, and those
    workflows need ongoing maintenance. However, that effort can accelerate
    later development by catching bugs early, reducing repetitive manual
    work, and making releases more consistent. Automated rollback, when
    configured and tested, can also reduce the impact of a failed deployment.
    The trade-off is that poor configuration or incomplete tests can give
    false confidence. I would therefore start with checks that address our
    most immediate risks and expand them as the project grows, while
    retaining human review.

    Our documentation pipeline made this risk concrete: it reported success
    while uploading an outdated PDF because change detection failed and
    compilation was skipped. This showed me that a successful status is
    only useful if the intended checks actually ran. For future workflows,
    I would verify both failure handling and the generated output, rather
    than relying on the status alone.

    \textbf{Shamil Canbolat:}

    CI/CD did not seem worth it to me at the beginning because the
    disadvantages are more apparent at first than the disadvantages. CI/CD
    can seem like a waste of time, requiring effort to configure and time
    to get used to using. It can be bloated and slow, requiring builds
    and automated testing for simple commits. As the development continues,
    time must be allocated to update and maintain checks and deployment tests.
    
    But the advantages outweigh the disadvantages. Bugs are caught early, 
    prevented more time being wasted on debugging later on. In addition to 
    saving time by eliminating manual builds and limiting human validation, 
    deployment tests force you to begin thinking of edge cases, risks, and
    output domain early on, making later system testing easier. Builds, in 
    our case PDF generation, has been very beneficial for catching formatting
    errors, seeing blame with highlighted colors, and comparing revisions to
    older commits. False positives and negatives are bound to occur, but this 
    will allow us to improve the deployment and improve the robustness of the 
    checking each time we catch a mistake with the pipeline.


    \item \textbf{What disagreements did your group have in this
    deliverable, if any, and how did you resolve them?}

    \textbf{Team Response:}

    Our main differences concerned the consequences of missing meetings
    and the roles and expectations of each team member. These discussions
    required more communication than simply dividing the deliverable
    because they established how we would hold one another accountable
    throughout the project.

    For attendance and missed commitments, I wanted expectations that
    were clear enough to act on while recognizing that illness,
    emergencies, and unavoidable conflicts can occur. I saw a risk in
    both extremes: vague consequences could allow repeated problems
    to continue, while an overly rigid response could treat a genuine
    difficulty as a lack of effort. Through discussion, we developed
    an approach with measurable triggers and a staged response.
    The charter begins with a private conversation and a recovery
    plan, followed by escalation to the teaching team if commitments
    remain unmet without an acceptable explanation. This gives the
    team a basis for taking action while allowing us to understand
    the circumstances first.

    We also differed over how specifically to define individual roles.
    While working on this section, I found that narrow assignments
    could make members feel restricted to one component, whereas
    making everything a shared responsibility left no clear person
    to coordinate the work. The resulting structure assigns broad
    lead roles while making software development, testing,
    documentation, and peer review responsibilities of every member.
    Assigning Moustafa as the notetaker provides a consistent owner
    for meeting records, while rotating the quality assurance
    coordinator each milestone distributes deliverable review duties.

    These discussions changed how I understood fairness within the
    team. Giving everyone the same number of titles does not
    necessarily create an equal workload, because implementation,
    coordination, and review require different amounts of effort
    at different stages. I now see the role assignments as a
    starting point that must be supported by clear task ownership
    and regular workload reviews.

    My main lesson was that expectations need to be discussed
    explicitly rather than assumed. Writing down the consequences,
    role boundaries, and shared duties helped turn our differing
    views into a practical agreement. However, agreement on the
    document does not guarantee that the process will work well.
    We will need to revisit it as the workload increases and check
    whether the responsibilities and responses remain fair and useful.

\end{enumerate}

\section*{Appendix --- Team Charter}

This charter sets out how the Squigglr team will work together,
distribute responsibilities, and address problems. All five members
will review and agree to these commitments before submission.
Changes will be discussed by the team and recorded in meeting notes.

\subsection*{External Goals}

Our primary goal is to complete a project that we are proud of and
can confidently present as a team. We want our work to meaningfully
address the problem and goals identified in the Problem Statement
and Goals document, with each member taking ownership of the
decisions and contributions that shape the final result.

We also aim to extend our learning by taking a software project
from initial planning and requirements through design,
implementation, testing, and final demonstration. Each member
will have opportunities to apply existing skills, explore
unfamiliar areas, and gain experience collaborating throughout
the development process.

Ultimately, we aim to earn a high grade that reflects the quality
of our work, our individual contributions, and our growth as a
team.

\subsection*{Attendance}

Reliable attendance supports shared understanding and timely
decisions. The following expectations apply to scheduled team
meetings, the weekly meeting with the project supervisor,
Dr.~Anand, and meetings with the teaching team. All five members
are expected to attend these meetings, subject to the absence
and emergency provisions below.

\subsubsection*{Expectations}

Members are expected to attend all agreed meetings, arrive on time,
and remain for the scheduled duration. Known absences, late arrivals,
or early departures should be communicated at least 24 hours in
advance whenever possible. Meeting times will be agreed with
consideration for members' availability.

Moustafa, or the assigned substitute notetaker, will record
attendance and action items. A member who misses a meeting will
review the notes and confirm their assigned actions within
24 hours of the notes being available, unless an emergency
prevents this.

\subsubsection*{Acceptable Excuse}

Acceptable reasons for missing a meeting or renegotiating a deadline
include illness, family emergencies, religious observances, essential
appointments, and unavoidable academic conflicts. Predictable
conflicts should be raised early so that the team can adjust its
schedule or redistribute work.

Forgetting a meeting, leaving work until the last moment, or accepting
a conflicting optional commitment without notifying the team will
not normally excuse an absence or missed deadline. Members are
expected to plan around known coursework and request help when
their workload becomes unmanageable.

\subsubsection*{In Case of Emergency}

A member experiencing an emergency will notify the team as soon as
reasonably possible. They need only communicate their availability
and the work affected; private personal details are not required.

The Project Manager will coordinate temporary reassignment of urgent
tasks. Available work and relevant notes should be shared when the
member is able to do so. If the disruption threatens a course
deadline or substantially affects the team's capacity, the Team
Liaison will contact the teaching team for guidance. Recovery
expectations will account for the member's circumstances.

\subsection*{Accountability and Teamwork}

All members share responsibility for a respectful working environment
and reliable contributions. The lead roles in
Section~\ref{sec:team-member-roles} support coordination, while each
member remains accountable for their assigned work.

\subsubsection*{Quality}

Members will arrive at meetings having reviewed the agenda and
relevant material, with a clear update on progress, blockers, and
decisions needed. Submitted work should satisfy the completion
criteria in its GitHub issue and be checked by its author before
review.

The team will aim to have review-ready contributions completed at
least 48 hours before each course deadline, leaving time for
integration and corrections. Different internal deadlines may be
agreed when dependencies require them, but they must be recorded
before the existing deadline passes.

Code changes will include appropriate tests, and documentation will
be checked against the applicable writing checklist and rubric.
Each substantial contribution will receive review from another
member. The milestone Quality Assurance (QA) coordinator will rotate
each milestone and track unresolved review findings. Authors remain
responsible for addressing feedback on their work.

\subsubsection*{Attitude}

Members will listen without interrupting, give constructive feedback,
and challenge ideas respectfully. Questions and requests for help
will be treated as opportunities to resolve problems early. Members
will acknowledge others' contributions and report mistakes or
uncertainties honestly.

Disagreements will first be discussed by the affected members,
focusing on the specific issue and its effect on the project.
If unresolved, the Project Manager will facilitate a discussion;
another agreed member will facilitate if the Project Manager is
involved. Persistent interpersonal problems will be referred to
the teaching team. Project decisions and actions will be recorded
without placing sensitive personal details in the public repository.

\subsubsection*{Stay on Track}

The team will plan around an average contribution of approximately
ten hours per member per week, including scheduled course activities.
Weekly task allocation will account for availability and the effort
required for implementation, research, coordination, and review.

Every substantive task will have an owner, completion criteria,
and a deadline in GitHub. Members will update their assigned issues
before each team meeting and report blockers as soon as they become
apparent. Progress will be reviewed weekly using completed work,
review participation, attendance, and outstanding tasks. Commit
counts alone will not determine whether contributions are fair.

The following events will trigger a workload and accountability
discussion:

\begin{itemize}
    \item Two unexcused meeting absences within four weeks.
    \item Three arrivals more than ten minutes late within four weeks,
    without prior notice or an acceptable reason.
    \item Two missed internal deadlines within four weeks, without
    an agreed extension or an acceptable reason.
    \item No substantive progress on assigned work across two
    consecutive weekly reviews, without a communicated blocker
    or agreed adjustment.
\end{itemize}

The first response will be a private discussion to understand the
cause, followed by a recorded recovery plan with specific tasks,
support, and deadlines. The team will review that plan within one
week. If commitments remain unmet without an acceptable explanation,
or the problem recurs during the following milestone, the Team
Liaison will seek guidance from the teaching team. Urgent work may
be reassigned to protect the project, with contributions recorded
accurately.

Members who complete work early or provide valuable support will
be acknowledged during meetings. Spare capacity will be used for
peer assistance, learning, or reducing later workload, rather than
automatically assigning more work to the same members.

\subsection*{Team Building}

Meetings will include a brief personal check-in to help members
communicate workload concerns and maintain positive relationships.
The team will aim to hold an optional social activity or informal
celebration after each major milestone. Activities will be
inexpensive and accommodate members' preferences and availability.

Occasional paired work sessions will provide opportunities to learn
from one another and build confidence in unfamiliar parts of the
project.

\subsection*{Decision Making}

The team will first seek consensus on significant decisions about
scope, technology, scheduling, and working practices. Members will
have an opportunity to explain their views, supported by project
requirements, evidence, and practical constraints.

If consensus cannot be reached in time, a decision will require
support from at least three of the five members. Absent members
will be given an opportunity to provide input asynchronously.
Unresolved decisions that threaten a milestone will be raised with
the advisor or teaching team.

Routine implementation choices may be made by the assigned developer
in consultation with the relevant lead, provided they remain within
agreed requirements and interfaces. Decisions affecting other
members' work will be communicated before dependent work proceeds.
Significant decisions and their rationale will be recorded in
GitHub issues or meeting notes.
