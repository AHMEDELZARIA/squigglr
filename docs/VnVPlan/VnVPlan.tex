\section{General Information}
\label{sec:general}

\subsection{Summary}
\label{sec:summary}

Squigglr is a website that helps children practise drawing on a touchscreen
with a stylus, and helps the adults supporting them see how that practice is
going. This plan covers its four main parts:

\begin{itemize}
  \item \textbf{Guided lessons.} An adult picks a lesson, like drawing a
    square, and the child works through stages that give less and less help:
    a demonstration, tracing a full outline, drawing between endpoints, then
    drawing with no guide. Squigglr moves to the next stage when an attempt
    passes. Squigglr can suggest going back a stage, but only an adult can make
    that change.
  \item \textbf{Creative drawing.} The child draws freely, and Squigglr can
    tidy up the drawing by adjusting the child's own strokes. The result stays
    editable and the original can always be restored.
  \item \textbf{Attempt records.} Each attempt keeps the stage, the
    difficulties the child ran into and the corrections they made, not just
    the final drawing.
  \item \textbf{Progress summaries.} Adults see how a child is doing over time,
    with attempts made with and without a guide kept separate.
\end{itemize}

The full requirements are in the SRS.

\subsection{Objectives}
\label{sec:objectives}

Our main objective is to build confidence that Squigglr is safe for children,
is actually what they and the adults supporting them need, and behaves
correctly. In order of priority:

\begin{enumerate}
  \item \textbf{Keep children safe and protect their well-being.} Squigglr is
    used by young children, some with autism, attention-deficit/hyperactivity
    disorder (ADHD) or other learning needs, so a failure that frustrates or
    upsets a child matters more than most bugs. Every safety-critical
    requirement (SRS Section~12.2) gets a test and a second, independent check
    in the safety inspection (Section~\ref{sec:safety-tests}).
  \item \textbf{Validate that we are building the right thing.} Our teaching
    assistant (TA), Chris, pointed out that for this project, validation and
    usability matter more than verification. Correctly built lessons that the
    specialists disagree with, or summaries adults can't understand, are still
    a failure. We validate with the supervisor, the specialists we interviewed
    and adult usability sessions (see the Software Validation section).
  \item \textbf{Show that Squigglr is usable and accessible.} Adults need to
    set up lessons and read summaries quickly, and the child's screens need to
    be easy to follow. We check this in usability sessions and against
    selected Web Content Accessibility Guidelines (WCAG) 2.2 success criteria.
  \item \textbf{Make sure lessons and records behave correctly.} Stage
    changes, pass and fail decisions, attempt limits and adult control are the
    core of the product, and an adult who sees a wrong record or summary could
    make a bad decision for the child. We test these at the minimum, default
    and maximum of every value the adult can set, and against the formal
    specification in SRS Section~9.2.
  \item \textbf{Protect children's data.} We keep records about children, so
    we check that a child is identified only by an identifier and an avatar,
    that no personal information is sent to the refinement service, and that
    only the right adults can see a child's records.
\end{enumerate}

Some values are still to be determined (TBD) in the SRS, such as the performance limits and
\texttt{REFINE\_TOLERANCE}. For each one, this plan says how and when we will
set it instead of leaving a placeholder (see the Symbolic Parameters
appendix).

With five people and one academic year, we are leaving these out:

\begin{itemize}
  \item \textbf{Testing with children.} No information is gathered from or
    about children and no study involves them (SRS CON-005 and CON-006), so every test and session uses adults or
    prepared attempts. This means the child's experience is judged by adults
    and the specialists rather than by children, which we accept as a limit
    of this plan.
  \item \textbf{Whether Squigglr improves children's drawing skills.} Showing
    that would take a long study with children, and Squigglr makes no such
    claim. We only check that the lessons work as specified and that the
    specialists think they make sense.
  \item \textbf{Third-party services and libraries.} We assume the
    authentication provider, the hosting and data storage service, the
    refinement model, the browsers and libraries like our testing frameworks
    are verified by the teams that make them. We only test how Squigglr uses
    them: what it sends, what it does with the result, and how it behaves when
    one is down. For example, we check that a refined drawing stays within
    \texttt{REFINE\_TOLERANCE}, not how good the model's output looks.
  \item \textbf{Waiting Room features} (SRS Section~25), such as letter
    tracing, finger drawing and offline use, since they are not part of the
    product we are building. This includes full WCAG conformance; we only
    check the selected success criteria.
  \item \textbf{Every device and browser.} We test on the test iPad with a
    stylus, on the browsers in our end-to-end tests (Section~\ref{sec:tools}),
    and on the other \texttt{SUPPORTED\_DEVICES} combinations we have access
    to (T-PERF-007), not on every touchscreen device.
\end{itemize}

\subsection{Relevant Documentation}
\label{sec:relevant-docs}

This plan builds on our other project documents. Here is how each one feeds
into our VnV work:

\begin{itemize}
  \item \textbf{Problem Statement and Goals} \citep{PSG}. Defines the problem
    and the goals Squigglr has to meet. Validation checks Squigglr against
    this problem, not just against the SRS, so it is what we go back to when
    the supervisor or the specialists question whether a feature is needed.
  \item \textbf{Software Requirements Specification (SRS)} \citep{SRS}. The
    main input to this plan. Every system test traces to an SRS requirement
    and uses its fit criterion as the pass condition
    (Section~\ref{sec:trace}). The symbolic constants give the boundary values
    we test at, and the formal specification in SRS Section~9.2 gives the
    expected output of the lesson tests.
  \item \textbf{Hazard Analysis} \citep{HA}. Each hazard lists the requirements
    that mitigate it, which can be functional, usability or safety-critical
    (Hazard Analysis Section~6). The safety-critical ones get the safety tests
    and safety inspection (Section~\ref{sec:safety-tests}), and the rest are
    covered by their functional and usability tests. The causes of each
    hazard tell us what failures the tests should try to cause, like
    repeated failed attempts or a lost connection.
  \item \textbf{Development Plan} \citep{DevPlan}. Names the language, coding
    standard, tools and continuous integration (CI) that our automated testing builds on
    (Section~\ref{sec:tools}), and the lead roles behind some of our VnV
    roles.
    Its target-tablet experiment is where the first performance limits come
    from.
  \item \textbf{Module Guide (MG)} \citep{MG}. Due in January 2027. Splits
    Squigglr into modules. The unit tests are organized by these modules, and
    the traceability between tests and modules checks that each one is
    covered. Design verification reviews it with the MG checklist.
  \item \textbf{Module Interface Specification (MIS)} \citep{MIS}. Also due
    in January 2027. Gives each module's interface, which is what the unit
    tests call and check against.
  \item \textbf{VnV Report} \citep{VnVReport}. Where we record the results of
    running this plan, including the measured values the performance tests
    report.
\end{itemize}

\paragraph{TA feedback from October~28.} In an informal meeting, we asked
Chris how to handle a few parts of the plan. His answers became rules for the
whole plan:
\begin{itemize}
  \item A value can stay TBD, but we have to say how it will be decided. Every
    TBD constant in the Symbolic Parameters appendix has to say how and when it
    is set, and Final QA checks this.
  \item There is no minimum number of tests per safety requirement, but we
    have to justify the number we pick. The safety tests explain why one test
    plus the safety inspection is enough (Section~\ref{sec:safety-tests}).
  \item One parameterized test with a table of cases counts as one test, as
    long as it is easy to follow. Each case gets a label and its own expected
    output, so it can be cited on its own.
  \item Full branch coverage is a good goal for safety-critical modules, and
    matters less for the user interface (Section~\ref{sec:tools}).
  \item For this project, validation and usability matter more than
    verification.
\end{itemize}

\paragraph{Review questions.} Every reviewer, in a PR review or in Final QA,
asks these about each test they check:
\begin{enumerate}
  \item Could someone else run it without asking the author? The input is
    specific and the expected output is explicit.
  \item Does it trace to a requirement, and is it in the traceability tables
    (Section~\ref{sec:trace})?
  \item Does it use symbolic constants instead of magic numbers, and does each
    constant have a value or a method in the Symbolic Parameters appendix?
  \item Does it try to break Squigglr, with boundary values, invalid input and
    failures, instead of only showing the normal case?
  \item For a review or inspection: does it say who does it, when, and with
    which checklist?
  \item Can we actually do it with our team, devices and schedule?
\end{enumerate}

\paragraph{Mutation check.} Mutation testing makes a small change to a program
and checks that some test fails. We apply the same idea to the plan. Each
member takes five requirements whose tests they did not write, including at
least two safety requirements. For each one, they write down a small,
realistic bug, such as a lesson ending one attempt after
\texttt{ATTEMPT\_LIMIT} instead of at it, or a refined point landing just
outside \texttt{REFINE\_TOLERANCE}. Then they find the test that would fail
because of it. If no test would fail, or the test's input does not include
that case, they open an issue for the test's owner. The check passes when
every bug is caught by at least one test. Each member needs about an hour for
this.

\paragraph{Final QA.} As QA coordinator for this milestone, Moustafa:
\begin{enumerate}
  \item checks that every SRS requirement ID appears in the traceability
    tables, with a script that compares the IDs in the SRS with the ones in
    this plan;
  \item checks that every TBD constant has a method, that no template comments
    are left, and that the PDF builds with no errors or undefined references;
  \item goes through the VnV and Writing checklists and the rubric, one item
    at a time;
  \item sends fixes in someone else's section to them as PR comments.
\end{enumerate}

\paragraph{Tracking findings.} Small fixes the team finds, like wording, go in
PR comments. Everything else, and all feedback from the TA and peer teams,
becomes a GitHub issue with the \texttt{review} label, one
assignee, and what closes it. An issue closes when the fix is merged or when
we record why we are not changing the plan.

\subsection{Implementation Verification}
\label{sec:impl-verification}

The implementation is checked in two ways: by running it and by reading
it. Running it covers:
\begin{itemize}
\item the system tests in this plan: the functional tests (T-LRN, T-CRT,

Section~\ref{sec:trace};
\item the unit tests for each module, chosen as described in the Unit Test
Description section once the MIS is done (the design documentation is due
on 18 January 2027);
\item the automated checks in Section~\ref{sec:tools}, which run these
tests on every PR.
\end{itemize}

tests only show behaviour on the inputs they choose. Reading finds paths

\paragraph{Inspection procedure.}
\begin{enumerate}
\item \emph{Planning} (moderator, two working days before the meeting): open
an issue labelled \texttt{review}. The issue names the files and commit,
the SRS requirements, the two inspectors and the checklist items. The
inspectors are chosen from people who did not write the files, according
to the commit history. For INS-REC, one of them is the Backend Lead unless
he wrote the code. If the Testing Lead wrote any of the files, the
milestone QA coordinator moderates instead.
\item \emph{Preparation} (each inspector alone, at most one hour): check the
code against every item, and list each finding in the issue with its file,
line and item.
\item \emph{Meeting} (at most one hour; moderator, inspectors and author):
go through the findings and mark each one major or minor. A finding is
major if it could change a pass decision, a count, a stage, a saved record
or what the child or adult sees, or if it breaks one of A1 to A8. Every
other finding is minor. The author answers questions but does not argue
findings.
\item \emph{Rework} (author): each major finding becomes its own issue
labelled \texttt{bug}, linked from the inspection issue and fixed by a PR.
Each minor finding is fixed, or closed with a reason.
\item \emph{Follow-up} (moderator): check every major fix. If there were
three or more major findings, inspect the changed code again before the
milestone.
\end{enumerate}
The inspection passes when no major finding is open on its date. When a
file is in both an inspection and the safety inspection at the same
milestone, the team holds one meeting: the SI steps first, then A1 to A9.

\paragraph{Walkthrough procedure.} The author shares the code on screen and
follows one scenario from input to saved result, for example a failing
attempt from the stylus events, through evaluation and the lesson rules,
to the saved attempt record. Listeners say where they cannot follow (item
13), and findings become GitHub issues. The walkthroughs on 6 December 2026
and 21 February 2027 prepare for the course code-review interviews on 9
December 2026 and 23 February 2027 (Development Plan). Findings from those
interviews are recorded the same way. From 24 January 2027, walkthroughs
also check items 11 and 12.

\paragraph{Feasibility and reporting.} An inspection takes about seven
person-hours: two hours of preparation for the two inspectors, a one-hour
meeting for four people, and one hour of planning and follow-up. The eight
inspections (two in PH-1, three in PH-2 and three smaller ones in PH-3)
take about 50 person-hours, or about ten for each member over the year.
Walkthroughs use time in the existing weekly meeting. The VnV Report lists
each inspection and walkthrough with its date, commit, participants,
findings by checklist item and severity, and status.

right, so a single case can be cited as, for example, \texttt{T-LRN-005 (c)}.

\subsubsection{Performance}
\label{sec:perf-tests}

These tests cover the performance requirements in SRS Section~12
(NFR-PERF-001 to NFR-PERF-005, NFR-PERF-008 and NFR-PERF-009). Timing
thresholds are written as symbolic constants. The SRS leaves their values to
this plan, so each constant in the Symbolic Parameters appendix states how its
value is set and when.

\paragraph{Test environment.} Squigglr is a web app, so in principle it runs on
any device with a modern browser, and on any network. Testing every device and
every connection is not realistic for a team of five, and it is not needed to
show that the requirements are met. The team will instead run the timing tests
on one tablet, an iPad with a stylus, which is the device the app is designed
around (SRS ASM-003). The tests run in a controlled setting: the iPad is
charged, Low Power Mode is off, every other app and browser tab is closed,
automatic updates are paused, and the iPad uses the same Wi-Fi network for
every run. Keeping these conditions the same means that a change in a measured
time comes from a change in Squigglr, not from the device or the network.
Automatic tests that do not need a physical stylus run in Playwright on a team
laptop under the same rules.

\paragraph{Why each test is repeated.} Even in a controlled setting, one
measurement can be slow by chance, for example when the browser collects
garbage. Each timing test is therefore repeated \texttt{PERF\_RUNS} times, and
the VnV Report gives the minimum, median, 95th percentile and maximum of the
measured times next to the threshold. A test passes only when the 95th
percentile and the maximum are both within the threshold. This way a single
slow run is still visible, but one unlucky run does not decide the result.

\paragraph{Limits.} Because the tests use one device and one network, they show
that Squigglr meets its timing requirements on the device it is designed for.
They do not show how it performs on older devices or slower networks. Other
browsers and devices are checked for correct operation, not speed, in
T-PERF-007.

\begin{enumerate}

\item{T-PERF-001: Stroke feedback latency\\}

Purpose: a child should see each stroke appear as they draw it; a visible delay makes drawing feel broken and can frustrate a child who is still building fine motor control.

Type: Dynamic, automatic (Playwright) and manual (physical stylus).

Initial State: a guided lesson is open at each stage where the child draws
(tracing, reduced guidance and independent drawing) with no earlier
attempts; no other tabs are open.

Input: the prepared stroke files \texttt{line.json}, \texttt{circle.json}
and \texttt{square-\allowbreak{}4-\allowbreak{}strokes.json}, replayed as pointer events by
Playwright, \texttt{PERF\_RUNS} times each; then \texttt{PERF\_RUNS}
strokes drawn by hand with the stylus on the iPad.

Output: for every stroke, the time from the last pointer event to the first
frame that shows the stroke is at most \texttt{FEEDBACK\_LATENCY\_MAX}.

Test Case Derivation: NFR-PERF-001 requires visual acknowledgement within
\texttt{FEEDBACK\_LATENCY\_MAX} of the final input point. Multi-stroke
shapes are included because they create the most rendering work per
attempt. The replayed strokes give exactly the same input on every run, so
they are the main measurement. A person cannot draw the same stroke twice,
so the hand-drawn strokes are not meant to be identical: only the time to
show each stroke is measured, not how accurate it is. They are there
because replayed events skip the real stylus input path on the iPad, which
could add its own delay.

How test will be performed: the replay script stamps
\texttt{performance.now()} at the last pointer event and in the next
\texttt{requestAnimationFrame} callback after the stroke is drawn. For the
manual runs, the iPad is connected to a Mac and the same interval is read
from a Safari Web Inspector timeline recording. Times are summarized as
described above.

\item{T-PERF-002: Refinement latency and canvas responsiveness\\}

Purpose: refinement runs on an outside service that can be slow, so this checks that the refined drawing arrives in time and that the child can keep drawing while it waits.

Type: Dynamic, automatic.

Initial State: the creative space is open with refinement on and the
refinement service reachable.

Input: the prepared drawings \texttt{house.json} and \texttt{sun.json}
are replayed and finished, \texttt{PERF\_RUNS} times each; during the wait,
a further stroke is replayed every 200~ms.

Output: the refined result appears within \texttt{REFINE\_LATENCY\_MAX} of finishing, and every stroke replayed during the wait is drawn
and saved without an error.

Test Case Derivation: NFR-PERF-002 requires both the time limit and an
unblocked canvas while the refinement is pending.

How test will be performed: the script records the time from the finish
action to the first frame showing the refined result, and checks the
canvas contents after each extra stroke.

\item{T-PERF-003: Progress summary load time\\}

Purpose: a parent or educator with a long history of saved attempts should not be left waiting for the progress summary to load.

Type: Dynamic, automatic.

Initial State: an adult account with one child profile whose history
holds \texttt{HISTORY\_SIZE\_LARGE} attempts across three lessons, logged
in, with the browser cache cleared.

Input: the adult opens the progress summary ten consecutive times.

Output: each time, the summary is fully visible within
\texttt{SUMMARY\_LOAD\_MAX}.

Test Case Derivation: the fit criterion of NFR-PERF-003 names ten
consecutive requests. A large history is used because load time grows with
the number of records.

How test will be performed: Playwright measures from the click to the
moment the last chart element is visible. The test is repeated with
histories of 10 attempts and \texttt{HISTORY\_SIZE\_LARGE} attempts, and
the two sets of times are reported together to show how load time grows
with history size.

\item{T-PERF-004: Deterministic stage result\\}

Purpose: the adult relies on pass and fail results to choose the next level, so the same drawing must always get the same result.

Type: Dynamic, automatic (unit test in Vitest).

Initial State: the stage evaluation module is loaded with the criteria
for each prepared stage.

Input: the prepared stroke files from T-PERF-001, plus
\texttt{circle-\allowbreak{}near-\allowbreak{}miss.json}, a drawing just outside
\texttt{STAGE\_PASS}, each evaluated ten consecutive times.

Output: all ten results for each input are identical, including the
pass or fail decision.

Test Case Derivation: NFR-PERF-004 requires the same strokes and criteria to
give the same result. The near miss checks that a borderline result does not
change between runs.

How test will be performed: a Vitest test calls the evaluation function
directly and compares every result with the first. A second run in
Playwright replays the same strokes through the user interface, to confirm
that input handling does not change the result.

\item{T-PERF-005: Submitting attempts after reconnection\\}

Purpose: home and school Wi-Fi can drop; a child's work done while offline must still reach the server once the connection returns, without being lost or saved twice.

Type: Dynamic, automatic.

Initial State: a guided lesson is open; the network is online.

Input: the network is set offline in Playwright; the prepared attempt
\texttt{circle.json} is completed; the network is restored. This is done
three consecutive times, then repeated with three attempts completed
while offline.

Output: after each reconnection, every attempt completed offline is saved
on the server exactly once, in the order made, and none is lost or
duplicated.

Test Case Derivation: NFR-PERF-005 names three consecutive runs. The
three-attempt case checks the order of a queue and catches duplicates.

How test will be performed: after each run, the script reads the child's
attempt records through the test database and compares them with the
attempts made. This test is shared with SAF-RAY-003 and SAF-SHA-003
(safety-critical tests below).

\item{T-PERF-006: Concurrent session capacity\\}

Purpose: several classrooms or households may use Squigglr at once; this checks that the speed limits still hold under that load.

Type: Dynamic, automatic (load test).

Initial State: the preview deployment, with \texttt{CONCURRENT\_CAPACITY}

Input: a load script runs \texttt{CONCURRENT\_CAPACITY} simulated sessions
at once; each replays a lesson of ten attempts and then opens the progress
summary.

Output: no request fails, and the measurements of T-PERF-001 to T-PERF-003,
taken in one extra session during the load, stay within their thresholds.

Test Case Derivation: NFR-PERF-008 requires the speed limits to hold under
the agreed load.

How test will be performed: the load script runs simulated sessions in
Playwright; one further session takes the timing measurements. The run
is repeated at a quarter, half and all of \texttt{CONCURRENT\_CAPACITY},
and the times are plotted against the number of sessions in the VnV Report.

\item{T-PERF-007: Squigglr keeps working until the end of the capstone\\}

Purpose: Squigglr must keep working on the supported devices and browsers at
least until the end of the capstone, the final demo on 15 March 2027 (PH-3 in

Type: Dynamic, manual.

Initial State: the release build at each milestone: the proof-of-concept
demo (PH-1, 23 November 2026), Rev~0 (PH-2, 1 February 2027) and the final

Input: on the iPad and on each other combination in

Test Case Derivation: the fit criterion of NFR-PERF-009.

How test will be performed: a team member runs the checklist by hand at
each milestone. Running it at the two earlier milestones, not only at the
final demo, means a browser update that breaks a feature is found while there

in the VnV Report.

\subsubsection{Safety-Critical Requirements}
\label{sec:safety-tests}

These tests cover the 18 safety-critical requirements in SRS Section~12.2,
which come from the \href{https://github.com/AHMEDELZARIA/squigglr/blob/main/docs/HazardAnalysis/HazardAnalysis.tex}{Hazard Analysis}. A failure here could harm a
child's well-being, privacy or records, so each requirement gets two
different kinds of evidence: a test below, and the safety inspection
described next. Every test below is dynamic except T-SAF-004, which checks
wording in templates and so is an inspection; T-SAF-016 combines a code
review with recordings on the iPad. The tests try to break each safeguard, for example by
having a child tap adult-only controls, cutting the connection during an
attempt, or switching between children on a shared device. All tests use
test accounts and prepared data only; no child takes part (SRS CON-006).
In these tests, ``the adult'' means the parent or educator responsible for
the child, and ``the adult check'' means the check in \texttt{ADULT\_CHECK}
(for example a PIN or password) that only the adult can complete.

\paragraph{Safety inspection (SI).} Before each revision (Rev~0 and
Rev~1), the code that implements each requirement below is inspected by two
team members who did not write it. The Backend Lead (Rayan Nasrallah) runs
the inspection and the Testing Lead (Muhammad Huzaifah) records the results.
For each requirement, the inspectors:
\begin{enumerate}
\item find every code path that triggers the safeguard, using the
test-to-requirement traceability table;
\item check that no path skips it, for example an adult-only action reachable
from a URL or a save that reports success before the server responds;
\item check that a dynamic test exercises each path, and add one if not;
\item check that errors are handled (every failed request leaves the
child's record unchanged and the adult is told) and that every input from
the browser is validated on the server;
\item record each finding as a GitHub issue labelled \texttt{safety}, and
re-inspect after the fix.
\end{enumerate}
The inspection passes when every requirement has no open \texttt{safety}
issue. Results are reported in the VnV Report.

\paragraph{Why this is enough.} Testing cannot prove that a safeguard always
works; it can only raise confidence that it does. One test per
requirement, each with cases chosen to break the safeguard, plus an
inspection that looks for paths the test missed, gives two independent
checks. A second dynamic test is added wherever the inspection finds an
untested path. The inspection covers only the code tied to these 18
requirements, because a full review of every module by two people is not
realistic in the time the team has. The rest of the code is covered by the
code checklist and the normal PR review.

\paragraph{How a lesson works.} Several of these tests check the limits in a
guided lesson, so this paragraph summarizes the lesson flow from SRS BR-002,
UC-002 to UC-005 and the state machine in SRS Section~9.2. The adult picks the
child and the lesson and completes the adult check. The child then watches a
demonstration and works through three stages in order: tracing a full
outline, drawing between endpoints, and drawing with no guide. An attempt
that meets \texttt{STAGE\_PASS} moves the child to the next stage
automatically, and a pass at the last stage completes the lesson. Failed
attempts are counted \emph{per stage}, and the count starts again whenever
the stage changes:
\begin{itemize}
\item after \texttt{DIFFICULTY\_STREAK} failed attempts in a row, Squigglr
suggests to the adult that the child go back a stage; the stage changes only
if the adult completes the adult check and accepts, and the child keeps
practising while the suggestion waits;
\item after \texttt{ATTEMPT\_LIMIT} failed attempts at one stage, the lesson
ends automatically, unless the child is improving, in which case the child
gets up to \texttt{ATTEMPT\_EXTENSION} more attempts, never more than
\texttt{ATTEMPT\_LIMIT\_MAX} in total at that stage;
\item after \texttt{LESSON\_IDLE\_PROMPT} with no input, Squigglr shows the
child a check-in, and after \texttt{LESSON\_IDLE\_END} with no input, the
lesson ends; time without input never counts as a failed attempt.
\end{itemize}
Because \texttt{ATTEMPT\_LIMIT} is always larger than
\texttt{DIFFICULTY\_STREAK} (SAF-RAY-008), the adult always receives the
suggestion before the lesson ends: the suggestion is the early warning and
the limit is the backstop. The adult sets these values for each child within
ranges set by the team. The examples below use illustrative values
(\texttt{DIFFICULTY\_STREAK} = 3, \texttt{ATTEMPT\_LIMIT} = 6,
\texttt{ATTEMPT\_EXTENSION} = 2, \texttt{ATTEMPT\_LIMIT\_MAX} = 8) to show
the expected behaviour; the tests themselves use the ends of each range.

\begin{enumerate}

\item{T-SAF-001: Adult-only actions need the adult check\\}

Purpose: choosing a lesson, choosing a starting stage, switching child and
accepting a go-back suggestion belong to the adult, so a child must not be
able to complete any of them.

Type: Dynamic, manual and automatic. Covers SAF-RAY-001.

Initial State: an adult account with two child profiles; child A is in a
guided lesson, and a go-back suggestion is waiting for the adult.

Input: on the lesson screen, the tester (acting as the child) taps every
visible control, taps the screen 50 times at random positions, opens the
web address of each adult-only action directly, uses the browser's back
and forward buttons and reloads the page. Each time the adult check
appears, the tester leaves it or enters a wrong answer. Finally, the tester
(acting as the adult) completes the adult check and accepts the suggestion.

Output: every adult-only action asks for the adult check, and none completes
until the check is passed. The suggestion stays waiting and the child can
keep drawing at the current stage. After the adult passes the check and
accepts, the child moves back one stage.

Example: child A fails three attempts in a row at the endpoints stage, and a
go-back suggestion appears. Child A taps ``accept''; Squigglr asks for the
adult check, which child A cannot complete, so the child stays at the
endpoints stage and keeps practising. The adult then completes the check and
accepts, and child A moves back to the tracing stage.

Test Case Derivation: SAF-RAY-001 and its hazards H-RAY-001 and H-RAY-006.
Random taps imitate a child who cannot read exploring the screen.

How test will be performed: a Playwright script performs the taps, web
addresses and navigation and checks the lesson state after each one; a
tester repeats the taps by hand with the stylus on the iPad.

\item{T-SAF-002: Notice on an unsupported device, browser or input\\}

Purpose: drawing results may be unreliable on a device or browser that is not
in \texttt{SUPPORTED\_DEVICES}, or when the child draws with a finger instead
of a stylus, so the adult must be told and can decide whether to continue.

Type: Dynamic, automatic and manual. Covers SAF-RAY-002.

Initial State: the adult has chosen a lesson; it has not started.

Input: (a) the lesson is started once with each combination in
\texttt{SUPPORTED\_DEVICES}, and once with each of three combinations that
are not in it: an older browser version, a phone-sized screen, and a browser
without pointer event support; (b) on the iPad, a supported lesson is
started and the first stroke is drawn with a finger; (c) the same, with the
first stroke drawn with the stylus.

Output: (a) for each unsupported combination, a notice the adult can read
appears before the first attempt; for each supported combination, no notice
appears; (b) the notice appears after the first stroke; (c) no notice
appears.

Test Case Derivation: the fit criterion of SAF-RAY-002 (H-RAY-002). A
browser cannot tell whether a stylus is connected before it is used, so
case (a) checks only what the browser reports (version, screen size and
pointer event support), and cases (b) and (c) check the input type the
browser reports for the first stroke (pen or touch).

How test will be performed: for (a), Playwright sets the browser version,
screen size and pointer event support for each combination and checks for
the notice; for (b) and (c), a tester draws on the iPad, once with a finger
and once with the stylus.

\item{T-SAF-003: Attempts kept until the server confirms them\\}

Purpose: an attempt must never look saved when it is not, or the adult would
make decisions from incomplete records.

Type: Dynamic, automatic. Covers SAF-RAY-003 and SAF-SHA-003.

Initial State: a guided lesson is open and online.

Input: (a) the connection is cut during an attempt; (b) the connection is cut
after the attempt is finished but before the server confirms the save, and
the page is then reloaded, and separately closed and reopened, while
offline; (c) the server returns an error for \texttt{FAILED\_SAVES} saves in
a row; (d) \texttt{FAILED\_SAVES} saves succeed normally.

Output: in (a) to (c), no attempt is shown as saved before the server
confirms it, the adult is told which attempts are not saved, and every
attempt is saved once the connection or server is back; in (d), no failure
message appears.

Test Case Derivation: SAF-RAY-003 and SAF-SHA-003 (H-RAY-002, H-SHA-003).
Case (d) checks that the warning does not appear when nothing failed.

How test will be performed: Playwright turns the network off and makes the
server return errors, then compares the server's records with the attempts
made.

\item{T-SAF-004: No diagnosis or comparison in summaries and exports\\}

Purpose: Squigglr is a practice tool, not an assessment, so no summary or
export may label, diagnose or compare a child, and each must say so.

Type: Static (inspection), manual. Covers SAF-RAY-004.

Initial State: the templates for every summary and export at that revision.

Input: one team member who did not write the templates reads each one.

Output: every template states that it describes practice only and is not an
assessment or diagnosis, and none uses a diagnostic label, judging wording
(for example ``struggling'', ``behind'' or ``below average'') or a comparison
with other children.

Test Case Derivation: the fit criterion of SAF-RAY-004 (H-RAY-003), which
asks for an inspection of every summary and export template. The team does
not intend to add diagnoses, so the realistic risks are a new template that
leaves out the required statement and wording that judges the child; a read
of each template catches both.

How test will be performed: once per revision (Rev~0 and Rev~1), as part of
the safety inspection; any problem is recorded as a GitHub issue labelled
\texttt{safety}.

\item{T-SAF-005: Lesson ends automatically at the attempt limit\\}

Purpose: a child must not be left repeating a stage they keep failing, so
the lesson must end by itself at the limit the adult set.

Type: Dynamic, automatic. Covers SAF-RAY-005.

Initial State: a child profile with \texttt{ATTEMPT\_LIMIT} and
\texttt{ATTEMPT\_LIMIT\_MAX} at the lowest values in their ranges; the test
is then repeated with the highest values.

Input: (a) at the tracing stage, the failing attempt
\texttt{circle-\allowbreak{}fail.json} is replayed until the lesson ends; (b)
the child passes tracing after a few failures, and the failing attempt is
replayed at the endpoints stage until the lesson ends; (c) a sequence of
attempts that improves enough to earn an extension is replayed until the
lesson ends.

Output: the lesson ends after exactly \texttt{ATTEMPT\_LIMIT} failed
attempts at one stage, or \texttt{ATTEMPT\_LIMIT\_MAX} when extended, with no
action from the child; failures at an earlier stage do not count at the new
stage; and the saved record matches the attempts made, including the
furthest stage reached.

Example: the sixth failed tracing attempt ends the lesson. In case (b), a
child who passed tracing after four failures still gets six attempts at the
endpoints stage. In case (c), an improving child gets attempts 7 and 8, and
the lesson ends after the eighth failure.

Test Case Derivation: SAF-RAY-005 (H-RAY-004). Testing both ends of the
ranges follows the supervisor's advice to test at the minimum and maximum
(SRC-008).

How test will be performed: Playwright counts the attempts and checks that
no attempt is accepted after the lesson ends.

\item{T-SAF-006: Limit endings are shown to the adult across repeated lessons\\}

Purpose: each time a lesson is done, it is a new lesson record, so the adult
must see how often the lesson ended at the limit across all of them; doing
the lesson again must not hide earlier failures.

Type: Dynamic, automatic. Covers SAF-RAY-006.

Initial State: as in T-SAF-005.

Input: the adult starts the lesson and it is run until it ends at the
limit; the adult then starts the same lesson again, and this is repeated so
the lesson is done three times. In the third run, an improving sequence
earns an extension before the lesson ends at the limit.

Output: the adult's view of that lesson shows three lesson records, each
ending at the limit, one extension, and every attempt from all three
records.

Example: the adult sees ``ended at the limit: 3 times; extended: once'' and
all 6 + 6 + 8 = 20 attempts.

Test Case Derivation: SAF-RAY-006 (H-RAY-005).

How test will be performed: the script compares the counts and the list of
attempts in the adult's view with the runs made.

\item{T-SAF-007: Attempts saved only to the active child\\}

Purpose: on a shared device, one child's attempts must never be saved to
another child's record.

Type: Dynamic, automatic and manual. Covers SAF-RAY-007.

Initial State: one adult account with three child profiles (A, B and C) on
one device.

Input: the adult switches between the children in the order A, B, A, C,
and each child makes two attempts; the connection is cut once during child
B's turn.

Output: every practice screen shows the active child's avatar, and every
attempt and suggestion is saved under the child whose avatar was shown when
it was made.

Test Case Derivation: SAF-RAY-007 (H-RAY-006). The lost connection checks
that a delayed save still goes to the right child.

How test will be performed: Playwright checks each child's records; a
tester checks by hand that each avatar can be recognized without reading.

\item{T-SAF-008: Adult-set values stay within their ranges\\}

Purpose: a mistyped or extreme value could give a child an impossible
lesson, so each value must stay within the range the team set and only the
adult may change it.

Type: Dynamic, automatic. Covers SAF-RAY-008.

Initial State: a new child profile with no values chosen.

Input: (a) no value is set; (b) each value is set to its minimum, its
maximum, one below the minimum and one above the maximum; (c)
\texttt{ATTEMPT\_LIMIT} is set equal to \texttt{DIFFICULTY\_STREAK}, and
\texttt{ATTEMPT\_LIMIT\_MAX} is set one below \texttt{ATTEMPT\_LIMIT}; (d) a
change is tried without completing the adult check.

Output: (a) each value is the middle of its range; (b) in-range values are
saved and out-of-range values are refused; (c) both settings are refused;
(d) nothing changes. The values in use are shown with the child's records.

Example: if the team-set range for \texttt{ATTEMPT\_LIMIT} were 4 to 10, an
unset value would be 7, values 4 and 10 would be saved, and 3 and 11 would
be refused. With \texttt{DIFFICULTY\_STREAK} = 3, an \texttt{ATTEMPT\_LIMIT}
of 3 is refused, because the lesson would end before the adult received the
go-back suggestion.

Test Case Derivation: the fit criterion of SAF-RAY-008 (H-RAY-007), using
boundary values on each side of each range.

How test will be performed: a Vitest test checks the validation function
with every case, and Playwright repeats cases (b) to (d) through the
settings screen and through direct server requests.

\item{T-SAF-009: Duplicate input events counted once\\}

Purpose: a stylus event reported twice must not change a drawing's result,
or a child could pass or fail for no real reason.

Type: Dynamic, automatic. Covers SAF-AHM-001.

Initial State: a guided lesson at the tracing stage.

Input: \texttt{square-\allowbreak{}4-\allowbreak{}strokes.json} is replayed
as recorded, then with every input event sent twice; then
\texttt{overlap-\allowbreak{}2-\allowbreak{}strokes.json}, two separate
strokes that cross, is replayed.

Output: the recorded points, classification and pass result are the same
with and without the duplicates, and both crossing strokes are kept.

Test Case Derivation: the fit criterion of SAF-AHM-001 (H-AHM-002).

How test will be performed: Playwright replays both versions and compares
the saved records.

\item{T-SAF-010: Drawing kept when the canvas changes size\\}

Purpose: rotating the iPad or resizing the window must not distort a drawing
or change its result.

Type: Dynamic, automatic. Covers SAF-AHM-002.

Initial State: a guided lesson with an attempt partly drawn.

Input: the window is resized and the iPad is rotated during the attempt;
then input events with positions outside the canvas, missing positions
(\texttt{NaN}) and very large values are sent.

Output: the order and relative positions of the points are unchanged, and
the classification is the same as without resizing; none of the invalid
points is counted or makes the attempt pass.

Test Case Derivation: the fit criterion of SAF-AHM-002 (H-AHM-003).

How test will be performed: Playwright resizes the drawing area and compares
the scaled points with the original; a Vitest test sends the invalid values
to the input handler.

\item{T-SAF-011: Every data request checks the account\\}

Purpose: one family's or school's data must never be reachable from another
account.

Type: Dynamic, automatic. Covers SAF-SHA-001, with T-SEC-001.

Initial State: two adult accounts, A and B, each with a child profile and
saved attempts.

Input: logged in as A, the tester sends requests to read, change and delete
B's child profiles, attempts, settings and summaries to every server
endpoint, then repeats them with no session and with an expired session.

Output: every request is refused, and none of B's data is returned or
changed.

Test Case Derivation: the fit criterion of SAF-SHA-001 (H-SHA-001).

How test will be performed: a script lists every endpoint from the code and
sends each request; the list is checked in the safety inspection, so a new
endpoint cannot be missed.

\item{T-SAF-012: No personal information sent to outside services\\}

Purpose: children's and adults' personal information must not leak to
outside services, including the refinement service.

Type: Dynamic, manual. Covers SAF-SHA-002.

Initial State: an account whose adult name and email, and the child
profile's identifier, are unique marker strings.

Input: the tester uses every feature, including refinement, while recording
all network traffic.

Output: no request to an outside service contains any marker string, and
requests go only to approved destinations.

Test Case Derivation: the fit criterion of SAF-SHA-002 (H-SHA-002). Unique
markers make any leak easy to find.

How test will be performed: the test runs in Chrome on a laptop; the
DevTools Network panel is exported as a HAR file and searched for the
markers and for destinations that are not approved.

\item{T-SAF-013: Logout after inactivity\\}

Purpose: an adult who walks away from a shared device must not leave their
account and their children's data open.

Type: Dynamic, automatic. Covers SAF-SHA-006.

Initial State: an adult is logged in.

Input: (a) no activity for \texttt{IDLE\_TIMEOUT}; (b) activity just before
\texttt{IDLE\_TIMEOUT}, then no activity.

Output: the adult is logged out after \texttt{IDLE\_TIMEOUT} of
inactivity and not before, and any later request using that session is
refused.

Test Case Derivation: SAF-SHA-006 (H-SHA-001). Case (b) checks that
activity restarts the timer.

How test will be performed: Playwright uses a controlled clock to move time
forward and checks the session.

\item{T-SAF-014: Feedback does not draw the missing part\\}

Purpose: feedback should show the child what is missing without drawing it
for them, so the record shows only the child's own work.

Type: Dynamic, automatic. Covers SAF-MOU-001.

Initial State: a guided lesson at each predefined difficulty.

Input: \texttt{square-\allowbreak{}missing-\allowbreak{}side.json}, an
attempt with one side missing.

Output: the feedback shows where the side is missing, and the strokes on
screen and in the record are the same before and after the feedback.

Test Case Derivation: the fit criterion of SAF-MOU-001 (H-MOU-004).

How test will be performed: Playwright compares the stroke data before and
after the feedback is shown.

\item{T-SAF-015: Assisted, independent and creative work kept apart\\}

Purpose: the adult must be able to tell what the child drew with an
on-screen guide from what they drew alone, so progress is not overstated.

Type: Dynamic and static, manual. Covers SAF-MOU-002.

Initial State: a prepared history of one lesson record holding 10 assisted
attempts, 10 independent attempts, and 5 creative space drawings made
separately.

Input: every summary and record view is opened.

Output: assisted and independent attempts are counted and shown separately,
no creative space drawing appears, and no view ranks or rates the child by
the number of attempts.

Example: a lesson record with 10 successful attempts while tracing and 2
while drawing alone is summarized as ``10 with a guide, 2 without'', never as
``12 successful drawings''.

Test Case Derivation: the fit criterion of SAF-MOU-002 (H-MOU-005). The
assisted or independent label belongs to each attempt, not to the lesson:
following FR-LRN-012, an attempt is assisted when it is drawn with an
on-screen guide (the tracing or endpoints stage) and independent when it is
drawn with no guide. One lesson record normally holds both kinds. Help from
an adult outside Squigglr, such as guiding the child's hand, is not detected
or recorded, and this test does not cover it.

How test will be performed: a tester checks each view against the prepared
history, and a Vitest test of the summary function compares the counts.

\item{T-SAF-016: No more than three flashes per second\\}

Purpose: rapid flashing can trigger seizures, so no child-facing screen may
flash more than three times in any one second.

Type: Static (code review) and dynamic, manual. Covers SAF-MOU-003.

Initial State: the code for every animation and transition on child-facing
screens, and Squigglr open on the iPad with a guided lesson ready.

Input: (a) a team member who did not write it reviews every animation and
transition used on child-facing screens, which are all defined in
Squigglr's own code and style sheets; (b) on the iPad, the screens that
animate (all feedback, the lesson-end message, the inactivity check-in and
the screen transitions) are screen-recorded.

Output: (a) no animation or transition changes brightness or colour more
than three times in any one second; (b) stepping through each recording
frame by frame, no one-second window has more than three flashes.

Test Case Derivation: the fit criterion of SAF-MOU-003 and WCAG 2.2
success criterion 2.3.1 \citep{wcag22}. Because every animation comes from
our own code, reviewing that code finds a flashing effect before it reaches
a screen; the recordings then confirm the result on the device, without
recording every screen.

How test will be performed: once per revision (Rev~0 and Rev~1), as part of
the safety inspection; any problem is recorded as a GitHub issue labelled
\texttt{safety}.

\item{T-SAF-017: Check-in and lesson ending after inactivity\\}

Purpose: a child may walk away during a lesson, and on a shared device
another child could carry on under their profile, so an idle lesson must
check in with the child and then end, with a clear record for the adult.

Type: Dynamic, automatic and manual. Covers SAF-RAY-009.

Initial State: a guided lesson at the endpoints stage, with
\texttt{LESSON\_IDLE\_PROMPT} and \texttt{LESSON\_IDLE\_END} at the lowest
values in their ranges; the test is then repeated with the highest values.

Input: (a) no input for \texttt{LESSON\_IDLE\_PROMPT}, then a touch; (b) no
input for \texttt{LESSON\_IDLE\_END}; (c) two failed attempts, then no input
until the lesson ends.

Output: (a) the check-in appears at \texttt{LESSON\_IDLE\_PROMPT}, the touch
dismisses it, and the lesson continues at the same stage; (b) the check-in
appears, then the lesson ends at \texttt{LESSON\_IDLE\_END}, the progress is
saved, and the adult's view shows the lesson ended for inactivity; (c) the
record shows exactly two failed attempts, so the idle time added none.

Example: with illustrative values of 60 seconds for the check-in and 120
seconds for the end, a child who stops drawing sees an animated character at 60 seconds; if nobody
touches the screen, the lesson ends at 120 seconds and the adult sees ``ended:
no activity''.

Test Case Derivation: the fit criterion of SAF-RAY-009 (H-RAY-006). Case (c)
checks that inactivity is never counted as failure.

How test will be performed: Playwright uses a controlled clock to move time
forward and checks the screen and the saved record; a tester checks by hand
on the iPad that the check-in can be understood without reading and does
not flash.

\end{enumerate}

\subsubsection{Operational and Environmental}
\label{sec:ops-tests}

These tests cover SRS Section~13 (NFR-OPS-001 to NFR-OPS-003): how
Squigglr reaches users through the browser and the outside services it
depends on.

\begin{enumerate}

\item{T-OPS-001: HTTPS only\\}

Purpose: all data between the browser and the server must be encrypted, so children's records cannot be read in transit.

Type: Dynamic, automatic and manual. Covers NFR-OPS-001.

Initial State: the preview deployment.

Input: in Chrome on a laptop, the tester uses every feature with the DevTools
Network panel recording, then opens the \texttt{http://} address of each
page. (DevTools cannot record traffic on the iPad, and the server's
behaviour does not depend on the device.)

Output: every request uses \texttt{https://}; every \texttt{http://}
address redirects to HTTPS or is refused.

Test Case Derivation: the fit criterion of NFR-OPS-001.

How test will be performed: the HAR from the normal HTTPS feature run is searched for any \texttt{http://} request; the intentional \texttt{http://} probes are checked separately for a redirect or refusal, and a Playwright test checks the redirects on every release.

\item{T-OPS-002: Error message when a provider is down\\}

Purpose: when an outside service is down, the adult should get a clear message instead of a broken screen.

Type: Dynamic, automatic. Covers NFR-OPS-002.

Initial State: an adult on the login page, and separately an adult in a
lesson.

Input: requests to the authentication provider, and then to the hosting
and storage service, are blocked to imitate an outage, and then
unblocked.

Output: an error message is shown for as long as the provider is
unavailable, no data is lost, and normal use resumes when it returns.
Refinement outages are covered by the FR-CRT tests.

Test Case Derivation: the fit criterion of NFR-OPS-002.

How test will be performed: Playwright blocks the provider's domain with
request routing and checks the page after each step.

\item{T-OPS-003: No installation\\}

Purpose: families and schools should be able to use Squigglr in a browser without installing anything.

Type: Dynamic, manual. Covers NFR-OPS-003.

Initial State: a fresh browser profile, with no extensions, on the iPad and
on each other combination in \texttt{SUPPORTED\_DEVICES} that the team has
access to.

Input: the tester opens the address, creates an account and runs a
lesson.

Output: everything works with no download, plugin, extension or install
prompt.

Test Case Derivation: the fit criterion of NFR-OPS-003.

How test will be performed: run together with T-PERF-007 and recorded in
the same table.

\end{enumerate}

\subsubsection{Maintainability and Support}
\label{sec:maint-tests}

These checks cover SRS Section~14 (NFR-MAINT-001 to NFR-MAINT-004). Most
are about the code and the process rather than running behaviour, so most
are reviews or CI checks.

\begin{enumerate}

\item{T-MAINT-001: Lessons are data, not code\\}

Purpose: new lessons should be added without changing code, so the app can
grow after the capstone.

Type: Static (code review) and dynamic, manual. Covers NFR-MAINT-001.

Initial State: the lesson catalogue at Rev~0.

Input: (a) a reviewer searches the source code for lesson content (shapes,
stage order, feedback wording); (b) a test lesson for a new shape is added
as a lesson file, edited and removed.

Output: (a) no lesson content is found in the source code; (b) the new
lesson appears, changes and disappears in the app with no code change or
rebuild, and its attempts are scored by the existing scoring.

Example: a lesson file holds the target outline as a list of points, the
guides for each stage (full outline and endpoints) and the feedback
messages. One scoring function compares the child's strokes with whatever
outline it is given (how far the drawn points are from the outline and how
much of it was covered), so a triangle lesson can be added as a new file in
the same way as the circle and square lessons.

Test Case Derivation: NFR-MAINT-001. This covers lessons that use the
existing scoring. A lesson that needs a new kind of scoring, for example
letters, where stroke order matters, needs new code and is outside this
test. How maintainers update lessons is still open in the SRS, so the
add, edit and remove step will follow the SRS wording once it is settled.

How test will be performed: the review is done by a team member who did
not write the catalogue module.

\item{T-MAINT-002: Finding the module for a lesson behaviour\\}

Purpose: a new developer should be able to find the code behind a lesson
behaviour quickly, so future fixes are practical.

Type: Static (walkthrough), manual. Covers NFR-MAINT-002.

Initial State: the code and the Module Guide (MG) at Rev~0.

Type: Static (document review), manual. Covers NFR-MAINT-003.

Initial State: the GitHub issues that create a top-level module, and the

Output: every issue asks for an interface description (the functions the

with the MIS that the requirement's title names.

Verification plan.

\item{T-MAINT-004: CI blocks style violations\\}

Type: Dynamic, automatic. Covers NFR-MAINT-004.

\subsubsection{Security}
\label{sec:sec-tests}

These tests cover SRS Section~15 (NFR-SEC-001 to NFR-SEC-006). They use
test accounts only. A child profile holds only a unique identifier generated
by Squigglr and an avatar chosen by the adult or the child (SRS BR-001,
NFR-SEC-004).

\begin{enumerate}

\item{T-SEC-001: An adult can only reach their own children\\}

Purpose: an adult must only ever reach their own children's profiles and records.

Type: Dynamic, automatic. Covers NFR-SEC-001, with T-SAF-011.

Initial State: accounts A and B, each with one child profile and
attempts.

Input: as A, read and modify B's child profile and attempt records
through direct server requests, using B's record IDs.

Output: every request is refused, and A's own data is unchanged.

Test Case Derivation: the fit criterion of NFR-SEC-001.

How test will be performed: a script sends the requests with A's session;
the access policies in the database are also reviewed in the safety
inspection.

\item{T-SEC-002: Logout ends the session\\}

Purpose: after logging out, nobody using the same device can continue the session.

Type: Dynamic, automatic. Covers NFR-SEC-002.

Initial State: an adult is logged in and the session token is copied.

Input: the adult logs out; the copied token is then used for an
authenticated request, three times.

Output: all three requests are refused.

Test Case Derivation: the fit criterion of NFR-SEC-002.

How test will be performed: Playwright reads the token before logging out
and sends the requests with it afterwards.

\item{T-SEC-003: Audit event for a blocked change to a saved record\\}

Purpose: saved attempts are the record the adult relies on; any blocked attempt to change one must be logged.

Type: Dynamic, automatic. Covers NFR-SEC-003.

Initial State: a saved attempt record.

Input: three requests to change the record, sent one after another.

Output: every request is refused, each creates an audit event, and no
event contains the record's contents.

Example: a request to change a saved attempt's result from fail to pass is
refused, and the audit event records the time, the account and the record's
identifier, but not the drawing or the result.

Test Case Derivation: the fit criterion of NFR-SEC-003.

How test will be performed: the script reads the audit log through the
team's database console and checks each event.

\item{T-SEC-004: Minimal personal data\\}

Purpose: collecting less personal data lowers the harm if data is ever exposed.

Type: Static (inspection), manual. Covers NFR-SEC-004.

Initial State: the screen for adding a child and the database schema.

Input: a reviewer lists every field on the screen for adding a child and
every column of the child profile in the schema.

Output: the only thing entered is the choice of avatar, and the
only child profile columns are the identifier, the avatar and the
adult-set values; there is no name, birth date, photo or other
child-identifying field.

Example: a field asking for the child's first name, even an optional one,
fails the test.

Test Case Derivation: the fit criterion of NFR-SEC-004. The schema is
included because a field can be stored without being on the screen.

How test will be performed: the review is done with the PIPEDA review in
T-COMP-001.

\item{T-SEC-005: Login failures and timeouts are logged privately\\}

Purpose: failed logins and timeouts are logged so problems can be found, without exposing private details in the logs.

Type: Dynamic, automatic. Covers NFR-SEC-005.

Initial State: a test adult account.

Input: ten failed logins and ten logouts by inactivity (using the
controlled clock from T-SAF-013); then a request for the audit log as
that adult.

Output: all twenty events are in the server-side log with a time stamp,
and the adult's request is refused.

Test Case Derivation: the fit criterion of NFR-SEC-005.

How test will be performed: Playwright triggers the events and the script
reads the log through the team's database console.

\item{T-SEC-006: Text inputs are sanitized\\}

Purpose: text typed into the app must not be able to run code or reach the database.

Type: Dynamic, automatic. Covers NFR-SEC-006.

Initial State: every text field and every server endpoint that accepts
text.

Input: the probe list \texttt{injection-\allowbreak{}probes.txt}, built from the OWASP
SQL injection and XSS filter-evasion cheat sheets, for example
\texttt{' OR '1'='1} and \texttt{<script>alert(1)</script>}.

Output: no probe changes a query or runs a script; each is stored or shown
as plain text or refused.

Test Case Derivation: the fit criterion of NFR-SEC-006.

How test will be performed: Playwright enters each probe in every field
and checks the page for script execution, and a script sends each probe
to every text endpoint.

\end{enumerate}

\item What went well while writing this deliverable?

confidence. Chris also told us that validation and usability matter more than
verification for this project, which is why they come right after safety in our
objectives. Dr.~Anand told us the same day to go back to the specialists we
interviewed, or people with similar qualifications, to validate the app.

Our process also went better than last time. In the SRS and Hazard Analysis we
had many merge conflicts, mostly because everyone added rows to the same
revision history table. This time Rayan suggested that everyone send their
revision history entries to Moustafa, who is doing the final quality check and
adds them all at the end. We also started from one set of shared notes in all
five VnV issues, so everyone knew which sections and test IDs they owned from
the start. Rayan, Huzaifah and Moustafa split their parts into small sub-issues
so each piece could be reviewed on its own, and Rayan's five branches merged
together without conflicts when tested.

\item What pain points did you experience during this deliverable, and how did
you resolve them?

\textbf{Team:} The main pain point was that writing the plan kept sending us
back to the SRS. Every test has to match a requirement, so each time a meeting
or a test changed how something should work, we had to go back through the SRS,
change it, and then check that our tests still matched it. The main changes came
from two meetings:
\begin{itemize}
\item \emph{Our supervisor meeting on October 28, 2026.} Dr.~Anand advised
that we should not collect children's personal details, so a child's profile
now holds only a generated identifier and an avatar instead of a first name
and username. This changed the business rules, the data dictionary, a
use case, a security requirement and the Hazard Analysis, as well as the
security test.
\item \emph{Our TA meeting on the same day.} Chris advised that a value left
as TBD should say how it will be decided, so every TBD performance value in
the SRS now points to the measurement method in this plan, and the other TBD
constants get a method in the Symbolic Parameters appendix.
\end{itemize}
We resolved this by keeping all of these SRS changes in one issue and one pull
request, separate from the VnV branches, and by re-reading each affected test
against the updated requirement before marking a branch ready for review.

Another pain point was that all five of us were writing the same \texttt{.tex}
file at the same time. Sections on separate branches could not see each other
until they merged, and some parts depended on others. For example, Moustafa's
